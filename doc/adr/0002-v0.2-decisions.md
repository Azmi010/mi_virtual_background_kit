Reference: [PRD-v0.2-v0.3.md](../dev/PRD-v0.2-v0.3.md), [TASKS-v0.2-v0.3.md](../dev/TASKS-v0.2-v0.3.md),

## Context

v0.2 adds a second package: the LiveKit adapter. One repo must serve two packages
released separately to pub.dev. Current starting position:

- One package at root; automatic publish via `v*` tags (T10.3, already working — tags
  `v0.1.0` and `v0.1.1` released).
- PRD-v0.2-v0.3 section 9 allows two development mechanism options: pub workspace
  or path dependency with a released-version dependency at release time.
- Sections 5–8 depend on spike T13.1 (LiveKit mechanism), T13.2 (shared track),
  T13.3 (smoothing), and T13.4 (slow devices) — all completed 11 November 2026.

## Decisions

### 1. Repo structure: one repo, core at root, adapter in `livekit/`

Per PRD-v0.2-v0.3 section 11. No separate repo, no federated plugin.

```
mi_virtual_background_kit/          # core package (publish from root)
  pubspec.yaml                      # + field workspace (bagian 2)
  livekit/                          # package mi_virtual_background_kit_livekit
    pubspec.yaml
  example/                          # di luar workspace, resolusi sendiri
```

### 2. Development: pub workspace (not path dependency)

- Root `pubspec.yaml` (core) adds `workspace: [livekit]`.
- `livekit/pubspec.yaml` adds `resolution: workspace` and a **hosted** core
  dependency: `mi_virtual_background_kit: ^0.2.0`. Inside the workspace, pub uses
  the local version; outside (consumers), pub uses the hosted version. No
  "swap path to hosted" step before publish.
- Core `sdk` rises `^3.5.0` → `^3.6.0` and `flutter` `>=3.24.0` → `>=3.27.0`
  (minimum workspace requirement at the time: all workspace packages `^3.6.0`). Noted in
  CHANGELOG 0.2.0 Breaking/Notes section.
- Amended 21 November 2026 (M-1): `livekit/pubspec.yaml` now declares
  `sdk: ^3.10.0` and `flutter: '>=3.38.0'`. `livekit_client 2.13.1` and newer
  require those floors, so the earlier adapter declaration allowed SDK versions
  that could not install its own dependency. Core keeps `^3.6.0` / `>=3.27.0`
  because it does not depend on `livekit_client`. Recorded as Breaking in the
  adapter CHANGELOG `Unreleased` entry.
- Attempting to exclude `livekit/` via root `.pubignore` has no effect: the
  adapter's `.pubignore` is only used when publishing from `livekit/`. T17.9
  audit with `dart pub publish --dry-run` at root shows the `livekit/` folder
  still enters the core archive (~1 KB). Accepted as-is — the adapter carries its
  own LICENSE and pubspec, so there is no API or license conflict.
- `example/` is not part of the workspace: it has its own `pub get` flow and build
  symlink (`tool/link_example_build.sh`), no change needed.

Verification (10 Nov 2026, scratch package + `dart pub publish --dry-run`):

- A publishable workspace root passes publish validation.
- The workspace folder still enters the core archive even with a root
  `.pubignore`; publish validation still passes (re-confirmed in T17.9).
- The `workspace` field on a package used as a dependency is safely ignored by
  the consumer's resolver (even pointing to a nonexistent path causes no error).
- Inter-package workspace dependencies with a hosted constraint resolve to the
  local version.

Rejected alternative — path dependency + manual swap to hosted before publish:
pub.dev rejects path dependencies at publish time, so the swap step is mandatory
and can be forgotten; workspace removes that step at no extra cost.

Accepted consequence: core consumers need Dart 3.6 / Flutter 3.27; adapter
consumers need Dart 3.10 / Flutter 3.38 as amended on 21 November 2026. The
original decision applied 3.6 / 3.27 to both packages.

### 3. Tag scheme: per package, two patterns

| Package | Tag | Pattern on pub.dev |
|---|---|---|
| core | `v0.2.0` (unchanged) | `v{{version}}` |
| adapter | `livekit-v0.2.0` | `livekit-v{{version}}` |

Core keeps the `v*` pattern: already configured and proven in T10.3, the
`v0.1.0`/`v0.1.1` tag history stays valid, no need to revisit pub.dev setup.
The adapter uses a package name prefix — the pattern recommended by dart-lang
documentation for multi-package repos.

Rejected alternative — prefix all packages (`core-v*` + `livekit-v*`): symmetric,
but requires changing the pub.dev tag configuration for the already-working core,
with no functional benefit.

### 4. Publish workflow (plan revision — implementation in Phase 15)

`.github/workflows/publish.yml` (core) **unchanged**. One new file added when
scaffolding the adapter (T15.1):

```yaml
# .github/workflows/publish_livekit.yml
name: Publish LiveKit adapter to pub.dev

on:
  push:
    tags:
      # must match the tag-pattern configured on pub.dev: 'livekit-v{{version}}'
      - 'livekit-v[0-9]+.[0-9]+.[0-9]+'

jobs:
  publish:
    permissions:
      id-token: write # Required for authentication using OIDC
    uses: dart-lang/setup-dart/.github/workflows/publish.yml@v1
    with:
      working-directory: livekit
```

Release order: **core first** (tag `v0.2.0` → wait for it to appear on pub.dev),
then the adapter (tag `livekit-v0.2.0`). This order is forced by pub: adapter
publish validation requires `mi_virtual_background_kit ^0.2.0` to already be
available hosted.

CI (`ci.yml`) was not changed in T12.4; workspace adjustments and adapter
analyze/test jobs come with T15.1 and the T17.4 version matrix.

### 5. LiveKit adapter mechanism: event-based re-attach (T13.1)

Decided 10 November 2026 from spike of 4 mechanisms × 7 stages on A1
(`livekit_client 2.13.1`; numbers in spike-results section T13.1).

**Decision: mechanism C** — the adapter calls core API `attach(mediaStreamTrack)`
once, then re-attaches the effect when the track restarts via the
`TrackStreamUpdatedEvent` event with track name matching. The adapter stays thin;
all effect logic stays in core (FR-14, FR-16).

Evidence: mechanism A (attach once) and B (`setProcessor`) lose the effect at S2
(camera switch) and do not recover — `restartTrack` calls `stop()`, which releases
the processor. C and D maintain the effect at all stages (teal ≥ 30%).

Rejected alternatives:

- **B/D (LiveKit's own `setProcessor` hook)** — the effect still disappears on
  restart for the same reason, and depends on LiveKit internal attachment points
  more prone to change between versions.
- **D versus C** — D only moves the dependency to an internal hook with no
  benefit; C is sufficient because recovery only needs the event.

Risk and mitigation: recovery depends on `TrackStreamUpdatedEvent` (internal
event) → track name matching, plus CI `livekit_client` lower/upper bound matrix
(T15.4) with explicit version range (T15.1). Spike tested 2.13.1.

### 6. Shared track handling: fully supported via redirect in the attach path (T13.2)

Decided 11 November 2026 (numbers in spike-results section T13.2).

**Decision: FR-19 option (b)** — `attach` selects the object that actually
processes frames; shared tracks fully supported on both platforms without a
`flutter_webrtc` fork:

- **Android**: registry wrapper identity compared with `VideoSource.videoProcessor`
  (two private fields + `getCapturerInfo`, `SharedTrackProbe`). Same → attach
  directly; different (shared, registry replacement, normal) → attach to the
  object owned by the source. Reflection fails → degrade to old behavior with log
  `reason=reflection-failed`, never crash.
- **iOS**: detect `track.processing` (KVC); nil → redirect to
  `videoCapturer?.delegate`, then fallback `retainedAdapter`. The kit retains the
  adapter across detach because the original wrapper is the adapter's sole strong
  owner (weak delegate) — without this, `getMediaTracks()` + detach kills the
  camera chain.

Evidence: teal ≥ 33% at all stages on A1; ≥ 37% S1/S3–S5 on iPhone 15 (S2 iOS 0%
= second `getUserMedia` chains independently — correct behavior; effect attaches
after normal attach).

Rejected alternative: **detection + clear `sharedTrack` error** (FR-19 option a)
— a planned limit, but full support turned out possible without a fork; still
kept as a degradation path if reflection/KVC changes.

Production: this path moved to a permanent location and tested in T14.1 (unit
test for reflection failure / `processing` nil, regression test for `toI420()`
encoder path). Risk: depends on `flutter_webrtc` private fields → held by version
range `^1.6.2` and safe degradation, per ADR 0001 no-fork principle.

### 7. Mask temporal smoothing design: adaptive EMA on the CPU path (T13.3)

Decided 11 November 2026 (numbers in spike-results section T13.3).

**Decision:**

- `adaptive` mode with default `maskTemporalSmoothing = 0.7` and `D0 = 0.06`:
  `out = prev * s + raw * (1 - s)` like a normal EMA, but history weight
  decreases toward 0 when mask innovation `d` exceeds `D0` — fast motion pulls
  in a fresh mask (no ghosting), stillness stays smooth.
- Value **0 = identical to v0.1** (FR-20 backward compatibility requirement;
  `none` mode verified = exact baseline).
- Selection numbers: flicker at stillness **−71% (A1) / −72% (iOS)**; ghosting
  `lag` ≤ 0,5% at all stages; fps without regression (iOS locked at 30,0).
- **Placement: CPU, at mask upload**, on both platforms — not GPU blend as in
  PRD draft section 9. Blend cost was not measurable within spike noise
  (dominated by metric instrumentation and debug build), the mask is small
  (49.152 px on Android), and adding a GL/Core Image pass is premature
  optimization. Revisit this decision only if production profiling (release,
  without metrics) shows a bottleneck there.
- History is reset on stage/effect/clear change.

New field `BackgroundQuality.maskTemporalSmoothing` (0..1, default 0.7):
non-breaking per section 9. The 0.4 value in the PRD draft example section 8.3
is replaced following this decision.

Rejected alternatives: **fixed non-adaptive EMA** — ghosting rises with s
(ema 0.7 → lag 3,3–6,4%, visible to the eye); **no smoothing (v0.1)** — baseline
flicker; **large `D0`** — chases the −50% flicker target during motion but opens
up ghosting.

Risk: PRD target −50% flicker during motion only reaches −27..30% with
`D0 = 0.06` (too conservative for motion) → T14.2 tuning debt: raise `D0` to
~0.10–0.12 then re-measure on the fixed test clip. Implementation note: iOS mask
is full size 640×480 (`segmentationWidth` does not shrink the mask on iOS) —
check together with T14.2/T14.3.

**Closed T14.2/T14.3 (12 November 2026, numbers in `doc/smoothing-raw/`,
`FlickerTestPage` sweep none/0.06/0.10/0.12 × still/motion):**

- Tuning debt **rejected**: `D0` 0.10 and 0.12 tested on A1 and iPhone 15 —
  motion flicker only dropped +20..32% on both platforms (no meaningful movement
  from `D0 = 0.06`) while `lag` rose 0,46% → 1,09–1,20% (exceeding the 0,5%
  limit). **`D0` default stays 0,06 and `s` stays 0,7 — zero code changes.**
- PRD §7 target −50%: **achieved at stillness** (A1 +50/+71/+79%; clean iPhone
  re-run +68/+59/+75%) and **not achieved during motion** in the tested D0
  range — recorded as a limitation, not an implementation failure.
- Platform parity confirmed on still and motion patterns; iPhone motion numbers
  vary between runs (−59%..+33%, operator motion script) — cross-platform claims
  use the same run per platform.
- First iPhone run failed validity for still (subject moved: `d` 5–7× baseline)
  — evidence that clip protocol must be strict; second run valid.
- fps without regression (A1 ~25, iPhone locked 30,0); `us/mask` still dominated
  by metric instrumentation per T13.3 findings.

### 8. Slow/32-bit device strategy (T13.4)

Decided 11 November 2026, entirely on A1 (numbers in spike-results section
T13.4; bench isolated from live pipeline, all numbers from debug build — release
absolute numbers are lower, relative comparisons valid):

| Candidate | Numbers | Decision |
|---|---|---|
| Model `selfie_segmenter_landscape` (144×256) | med 87,9 ms vs 133,1 (−34%), agree 98,9% / IoU 96,8%, same size 250 KB | **Selected** — replacement for square as default; **implemented in T14.5** (13 Nov 2026, Android): A1 live inference 141 → 93 ms (−34%), gap 329 → 295 ms with width 256, fps without regression |
| `always` strategy (segmentation each time worker is idle) | gap 158 ms vs 318 ms (mask 2× fresher), fps identical 24,9–25,0 | **Default candidate**; locked after T17.1 (battery/thermal; duty cycle 82% vs 40%) — if T17.1 results are bad, return to `current` |
| `current` strategy (v0.1 mapping) | gap 318 ms, fps 25,0 | Applies as baseline until T17.1; FR-12 remains the last protection |
| `budget` strategy | gap 405 ms (stalest) | **Rejected** |
| MediaPipe GPU delegate | SIGABRT `image_frame.cc:102` format UNKNOWN, 3 runs including after detach | **Rejected** — GPU result conversion fails → uncaught native `abort()`, independent of other segmenters |
| Model `selfie_multiclass_256x256` | med 2.430 ms (18×), init 835 ms, 16,4 MB; quality 99,7% | **Rejected** — binary is sufficient (99,7% agreement), latency and size unreasonable |
| Readback width 144 | only −9% | **Rejected** as the main lever; landscape + 144 combo tested in T14.5 — result: gap **210 ms (−36% vs baseline 329 ms)**, inference 73 ms (within interval bracket 5), but **still not made default** because combo visual quality has not been measured; so a slow-device option (`BackgroundQuality(segmentationWidth: 144)`) |

GPU rejection quote:
`Abort message: 'image_frame.cc:102] Check failed: ImageFormat::UNKNOWN != format_ (0 vs. 0)'`
— stack `TaskRunner → ImageSegmenter.convertToTaskResult →
PacketGetter.nativeGetImageWidth`.

Risk: `always` impacts battery and thermal, not yet measured → locking condition
in T17.1; until then `current` stays the production default. Landscape model
tested on landscape camera buffer (hook always receives camera buffer, not UI
crop) — portrait source not tested, low risk.

### 9. API change policy for 0.x (T12.5, decided 10 November 2026)

  1. **Adding a subclass of `sealed class VirtualBackgroundEffect`** (e.g. `VideoEffect`
     in v0.3) and **new error codes in the `BackgroundException` hierarchy** (e.g.
     `invalidVideo`) may land in a **minor** version, not a patch — consumers with
     exhaustive `switch` will break. Required: CHANGELOG entry labeled
     **Breaking:**, note in README/FAQ if behavior is misleading, and confirmation
     via the "Public API change" checkbox in the PR template.
  2. **New `BackgroundQuality` fields** (e.g. `maskTemporalSmoothing`, `autoRecovery`)
     are non-breaking **as long as** they have a default value that preserves
     previous version behavior. A field without a default value is treated like
     item 1.
  3. Other changes that remove or alter a public API signature follow item 1:
     minor + Breaking label.
  4. The **Breaking** label is only for changes that force consumers to change
     code; purely additive API additions are not labeled.
